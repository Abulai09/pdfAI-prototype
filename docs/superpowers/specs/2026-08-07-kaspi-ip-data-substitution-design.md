# Подстановка реквизитов в шаблон Kaspi ИП — дизайн

Дата: 2026-08-07
Статус: согласован, готов к плану реализации

## Задача

Новый режим в приложении: пользователь не задаёт целевой доход, а вводит **свои реквизиты**, и программа выдаёт выписку Kaspi ИП с ними. Суммы, даты операций, назначения платежей, шрифт и позиции остаются ровно такими, как в шаблоне.

Меняются пять текстовых полей шапки:

| Поле | Формат | Длина | Вхождений в шаблоне |
| --- | --- | --- | --- |
| Лицевой счёт | `KZ` + 2 цифры + 16 буквоцифр | всегда 20 | 13 |
| Период | `ДД.ММ.ГГГГ - ДД.ММ.ГГГГ` | всегда 23 | 1 |
| Дата последнего движения | `ДД.ММ.ГГГГ ЧЧ:ММ` | всегда 16 | 1 |
| ИИН/БИН | 12 цифр | всегда 12 | 17 |
| Наименование клиента | произвольный текст | переменная | 1 |

## Принятые решения

1. **Шаблон встроенный.** Пользователь ничего не загружает — программа берёт зашитый файл (нынешний `IP2.pdf`).
2. **Даты операций не сдвигаются.** Период — то, что ввёл пользователь; таблица не трогается. Следствие принято сознательно: при периоде, не покрывающем `18.07.2025 – 18.07.2026`, часть операций окажется за его границами (при периоде по умолчанию — 14 дат из 247). Интерфейс показывает мягкое предупреждение, но не блокирует.
3. **Недостающие глифы вшиваются в шрифт**, а не вызывают отказ.
4. **Лицевой счёт и ИИН меняются везде**, включая 28 вхождений внутри «Назначения платежа», а не только 2 в шапке.
5. **Шаблон хранится вне git** — `templates/kaspi_ip.pdf`, папка в `.gitignore`, путь переопределяется переменной `PDFAI_KASPI_IP_TEMPLATE`. В `.exe` попадает через `build.spec`.

## Замеры, на которых стоит дизайн

Все выполнены на `C:\Users\Abylay\Desktop\testpdf\kaspiPay\IP2.pdf` (101 страница, `/Producer: iTextSharp.LGPLv2.Core 1.6.7.0`).

**Шрифт один на весь документ** — `OJSMTG+ArialMT`, ресурс `F1`, `/CIDToGIDMap /Identity`. Второго шрифта, из которого можно было бы позаимствовать глиф, нет вовсе.

**Subset — 133 символа, и все 133 совпали байт-в-байт с `C:\Windows\Fonts\arial.ttf`** при сверке по GID. Это обычная выборка стокового Arial с сохранением исходных GID (CID `023A` = `А` = GID 570 в arial.ttf). Значит вшивание недостающих глифов работает тем же приёмом, что уже отлажен для жирных цифр Halyk, и gate «сверь присутствующие, потом доверяй» на этом файле проходит идеально.

**Чего в subset'е нет:** заглавных `Щ`, `Ъ`, `Ы`, `Ю` и латинской `W`. Это не редкий случай: имена в этом поле набраны заглавными, а `Ы` в казахских ФИО встречается постоянно. В самом `arial.ttf` есть всё нужное, включая казахские `Ә Ғ Қ Ң Ө Ұ Ү Һ І` — ограничений по алфавиту не будет. GID недостающих: `Щ`=595, `Ъ`=596, `Ы`=597, `Ю`=600, `W`=58.

**Компрессор потоков менять не нужно.** Все 103 потока шаблона воспроизводятся `zlib.compress(данные, 6)` побайтово — `iTextSharp` пишет ровно как python-zlib. Это противоположность Halyk (`PDFsharp`, 0 из 56), где для того же признака понадобился отдельный порт компрессора. Наш нынешний `zlib.compress` здесь и есть верный почерк; `check_stream_compressor` такой файл пропускает своей же веткой «оригинал сам пишет как zlib».

**Свободное место под наименование клиента** — значение занимает 148 pt, до края строки ещё ~482 pt, соседей на строке нет. Запас втрое.

## Архитектура

### Новые модули

`kaspi_ip_data_service.py` — подстановка реквизитов. Отдельно от `kaspi_ip_pdf_service.py`: там пересчёт сумм и коридоры ISI, здесь только текст; смешивать — раздувать и без того большой файл. Публичный интерфейс:

```
class KaspiIPFields:   # dataclass: account, period_from, period_to, last_movement, iin, client_name
def default_fields() -> KaspiIPFields          # значения по умолчанию от текущей даты
def validate_fields(f) -> list[str]            # ошибки ввода, пустой список = всё хорошо
def substitute_fields(template: bytes, f) -> bytes
```

`kaspi_ip_glyphs.py` — замороженные контуры Arial для символов, которых может не оказаться в subset'е, по образцу `halyk_bold_digits.py`: байты извлекаются офлайн один раз и фиксируются в исходнике, рантайм не читает `arial.ttf` с диска и не тянет `fontTools`.

### Переиспользуемое

Из `pdf_service`: `build_dynamic_cmap`, `_rebuild_xref_table`, `_patch_truetype_glyphs`, `_read_truetype_glyph`, `_op_separators`, `_fmt_coord`.

`_w_array_insert_sorted` и `_cmap_add_mappings` сейчас живут в `halyk_pdf_service.py`, но понадобились второй раз. **Переносятся в `pdf_service.py`**, где уже лежат остальные общие низкоуровневые помощники; `halyk_pdf_service` импортирует их оттуда. Тянуть их из halyk-модуля в kaspi-модуль было бы неверной зависимостью.

### Как выполняется замена

**Четыре поля фиксированной длины** — побайтовая замена той же длины в потоке страницы. Вёрстка не меняется вовсе: ширины не пересчитываются, `Td` не трогаются, переносы строк внутри «Назначения платежа» остаются как были. Это и делает решение №4 (менять счёт и ИИН везде) практически бесплатным.

**Наименование клиента** — переменная длина, поэтому идёт через тот же механизм `X Y Td (CID) Tj`, что и остальной писатель Kaspi ИП. Поле лево-выровнено и соседей на строке не имеет, поэтому X начала **не пересчитывается вовсе**; ширина по реальным метрикам `/W` (`_primary_glyph_advances`, уже существует) считается только для того, чтобы проверить, что текст влезает в отведённые ~482 pt, и отказать, если нет.

**Недостающие глифы.** Перед записью собирается множество символов нового текста, которых нет в subset'е. Для каждого: контур вшивается в `glyf`/`loca`, ширина — в `/W`, соответствие — в `ToUnicode`. Все три правки готовятся из одного снимка байт и применяются либо все, либо ни одной — та же дисциплина атомарности, что у вшивания цифр Halyk. Gate: если хотя бы один уже присутствующий глиф не совпал с эталоном, функция не доверяет эталону для этого файла целиком и возвращает отказ.

### Валидация

| Поле | Правило |
| --- | --- |
| Лицевой счёт | `^KZ\d{2}[0-9A-Z]{16}$` |
| ИИН/БИН | ровно 12 цифр |
| Период | обе даты `ДД.ММ.ГГГГ`, начало ≤ конца |
| Дата движения | `ДД.ММ.ГГГГ ЧЧ:ММ` |
| Наименование | непустое; отказ, если не влезает по ширине |

Ошибки — HTTP 400 со списком полей. Отдельно, **не блокируя**: предупреждение, если период не покрывает диапазон операций шаблона.

Значения по умолчанию: период = «сегодня минус год … сегодня», дата движения = текущее время, остальные поля пустые.

### API и интерфейс

`POST /process-kaspi-ip-data` — JSON с пятью полями, ответ — PDF. Дефолты отдаёт `GET /kaspi-ip-data-defaults`, чтобы форма не считала их на клиенте.

В `static/index.html` — новая вкладка рядом со «Скоринг / Бизнес / Проверка», пять полей с предзаполненными значениями по умолчанию и кнопкой запуска.

## Проверки

`tests/scripts/verify_kaspi_ip_data.py` — прогон шаблона через подстановку с набором вводов, и на каждом результате:

1. **Ничего лишнего не изменилось** — множество сумм и дат операций совпадает с шаблоном; число страниц то же; `is_repaired` = False.
2. **Новые значения на месте** — все пять полей извлекаются из текстового слоя ровно в введённом виде, и старых значений в документе не осталось ни одного.
3. **Позиции и шрифт** — `find_line_overlaps`, набор шрифтов и кеглей не изменился (`check_fonts`).
4. **Стиль сериализации** — `style_check`.
5. **Плотность subset'а** — вшиты ровно те глифы, что реально печатаются, лишних нет.

Отдельно — юнит-тесты без фикстур на `validate_fields` и `default_fields`.

## Что сознательно не делается

- Даты операций не сдвигаются вслед за периодом (решение №2).
- Суммы не пересчитываются вовсе — это отдельный существующий режим.
- Валюта счёта, входящий и исходящий остаток не редактируются: они связаны с суммами таблицы, а суммы мы не трогаем.
