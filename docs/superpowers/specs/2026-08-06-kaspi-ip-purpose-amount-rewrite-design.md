# Kaspi ИП: переписывать сумму внутри текста «Назначение платежа» — Design

## Проблема

`kaspi_ip_pdf_service._purpose_repeats_amount` (существует с 2026-08-03/04) детектирует строки, где отмасштабированная сумма транзакции продублирована в свободном тексте «Назначение платежа» («…по сч №91 от 10.07.26 Сумма 75 000-00 теңге без НДС»). Сейчас это ТОЛЬКО диагностика: колонка «Кредит» переписывается на новую сумму, а текст назначения остаётся со старой — итоговый документ математически корректен (баланс сходится, наложений нет, ни одна автоматическая проверка этого не видит), но противоречит сам себе на глаз: «Кредит 5 346 000» рядом с «Сумма 75 000-00» в тексте той же строки.

Замораживание таких строк (не масштабировать) уже пробовалось и было откачено 2026-08-04: на `IP4.pdf` под это правило попадает 42.8% всего кредита, на `kaspiIP.pdf` — 8.8%; замороженный кредит нельзя подтянуть к цели, ISI падает до 0.50/0.56 против жёсткого порога 0.60 в `validate_kaspi_ip` — фиксированная проверка начинает валиться на ВСЕХ целях, включая ранее проходившие. Настоящее решение — переписать число ещё и внутри текста, не замораживая строку.

## Область охвата (измерено 2026-08-06 на реальных файлах `testpdf/kaspiPay`)

| файл | affected (amount_in_purpose) | сумма целиком в одной визуальной строке | разорвана переносом |
|---|---|---|---|
| IP4.pdf | 82 | 80 (97.6%) | 2 (2.4%) |
| kaspiIP.pdf | 16 | 15 (93.75%) | 1 (6.25%) |
| IP2.pdf / IP3.pdf | 0 | — | — |

Все 98 затронутых строк — кредитные (0 дебетовых). Ключевая находка формата: каждая визуальная строка ячейки «Назначение платежа» — это ОДИН оператор `1 0 0 1 X Y Tm (...) Tj` с АБСОЛЮТНЫМ позиционированием (не цепочка относительных `Td`); перенос строк уже зафиксирован оригинальным генератором как набор независимо позиционированных строк, не единый reflow-блок.

**В рамках этой задачи:** точечная замена цифрового прогона внутри строки, когда он целиком лежит в одной такой `Tj`-строке — покрывает 95 из 98 (97%) реальных случаев.

**Вне рамок (сознательно):** 3 строки, где перенос разрывает число посередине (напр. «…Сумма 1 080» / «000-00 тенге…») — это требует реализовать word-wrap оригинального генератора и переписать весь абзац разом, включая Y-позиции всех его строк. Отдельная, более сложная задача; не делается здесь. Такие строки остаются как сегодня — сумма в тексте не совпадает с колонкой «Кредит», диагностика видит их и раньше (`_purpose_repeats_amount` срабатывает независимо от того, попадёт ли строка в этот новый механизм).

## Архитектура

Расширяется существующий однопроходный `tm_pat.sub(replace_tm, decompressed)` в `process_kaspi_ip_pdf` — тот же проход, что сейчас переписывает ячейки «Дебет»/«Кредит». Внутри `replace_tm` уже есть ветка:

```python
parsed_cell = _parse_amount_cell(decoded)
if parsed_cell is None:
    return match.group(0)
```

— строка, не похожая на чистое число (в т.ч. любая строка назначения платежа), сейчас возвращается без изменений. Новый код вставляется В ЭТУ ветку: если `_parse_amount_cell` не распознал ячейку как число, проверяем очередь `page_replace_purpose` (см. ниже) — и если строка там значится, переписываем её текст на месте.

Никакого второго прохода по файлу и никакого нового учёта смещений: `re.sub` уже обрабатывает произвольное изменение длины совпадения within один вызов, а внешний учёт `cumulative_offset`/пересборка xref не зависит от ТОГО, что именно изменилось внутри распакованного стрима.

## Препроход: поиск и очередь

Перед основным байтовым проходом (там же, где сегодня строятся `page_replace_credit`/`page_replace_debit`) добавляется препроход по `stmt.transactions`:

```python
page_replace_purpose: Dict[int, Dict[str, deque]] = defaultdict(lambda: defaultdict(deque))
```

Для каждой транзакции с `amount_in_purpose=True`, `is_scaleable=True` и `abs(new_amount - amount) >= 0.005`:

1. Находится строка (та же грануляция построчного разбора, что уже даёт `_page_lines_with_y` — один `Tj` = одна визуальная строка), содержащая цифровой прогон суммы, и позиция/формат прогона внутри НЕсжатого (не компактного) текста этой строки.
2. Если прогон разорван между двумя строками — транзакция пропускается (в очередь не попадает).
3. Иначе — очередь пополняется: `page_replace_purpose[page][старый_текст_строки].append(новый_текст_строки)`, где новый текст строки — оригинальная строка с заменённым внутри цифровым прогоном (остальной текст байт-в-байт тот же).

Новая функция для поиска (замена `_purpose_repeats_amount`'а «просто bool» на «bool + позиция + формат»):

```python
def _locate_purpose_amount(line: str, amount: float) -> Optional[Tuple[int, int, str, str, bool]]:
    """Возвращает (start, end, thousands_sep, decimal_sep, has_decimal) —
    позицию цифрового прогона суммы В ЭТОЙ строке (в её НЕкомпактных
    координатах) и обнаруженный формат, либо None, если сумма НЕ находится
    ЦЕЛИКОМ в этой строке (см. _purpose_repeats_amount для матчинга по
    компактной форме — здесь то же самое, но с сохранением позиции для
    последующей замены).

    has_decimal=False — сумма в тексте написана БЕЗ копеек вовсе (напр.
    «Сумма 75000 тенге», без «-00»/",00" на конце) — _purpose_repeats_amount
    матчит только целую часть, поэтому такой случай реален и должен
    воспроизводиться формататором без добавления несуществовавших копеек."""
```

`_purpose_repeats_amount` (диагностика в `parse_kaspi_ip_statement`, печатающая долю в логах) не меняется — остаётся независимой проверкой «эта сумма где-то повторяется», работающей на ПОЛНОМ (не обрезанном до 120 симв.) назначении, как и сейчас.

## Формат числа

`_format_purpose_amount(new_amount: float, thousands_sep: str, decimal_sep: str, has_decimal: bool) -> str` — строит новый цифровой прогон в ТОЙ ЖЕ нотации, что и оригинальный (принцип «повторить почерк оригинала», как `_op_separators`/`_fmt_coord_debet`), где все параметры — не константы, а то, что реально нашлось в ЭТОЙ конкретной строке (`_locate_purpose_amount`). Наблюдаемые в реальных файлах варианты: `145000-00` (без разделителя тысяч, `-` перед копейками), `65 000,00` (пробел, `,`), `475 000-00` (пробел, `-`); `has_decimal=False` — сумма без копеек вовсе.

## Gate по ширине ячейки

У ячейки назначения платежа нет декларативной X-границы в PDF (это proза, а не таблица с фиксированной шириной колонки), поэтому граница измеряется эмпирически из самого документа: максимальный правый край (`bbox[2]`, PyMuPDF) среди ВСЕХ строк назначения платежа по всему оригинальному документу — это эмпирически достоверный «край, дальше которого сам генератор никогда не заходил» (тот же принцип «граница берётся из файла, а не выдумывается», что и в `check_column_alignment` для Kaspi Gold).

Для новой (заменённой) строки ширина считается по реальным метрикам шрифта (`GLYPH_EM`, из `_primary_glyph_advances` — уже используется для колонки «Дебет»). Если `x0_строки + новая_ширина` превышает измеренный эмпирический край (без запаса — по образцу «Дебет», где тоже не закладывается искусственный допуск) — тихий отказ: транзакция НЕ попадает в очередь `page_replace_purpose` вовсе (решение принимается в препроходе, не в момент записи байт), текст назначения остаётся прежним. Тот же fail-safe-принцип, что у вшивания глифов в Halyk: попытка либо строго корректна, либо не делается вовсе.

## Проверки

- `verify_kaspi_ip_file.py` (и `verify_any_file.py` — обе точки, по конвенции проекта): новая `check_purpose_amount_consistency(orig_bytes, out_bytes)`. Для каждой транзакции оригинала, где `amount_in_purpose=True` и сумма при данной цели меняется, — либо в РЕЗУЛЬТАТЕ текст назначения содержит НОВУЮ сумму (успех, не сообщение), либо это документированный skip (перенос строки / gate по ширине) — помечается `[guard]` с причиной, не FAIL. Формула та же, что у `check_bold_row_uniform`/`[glyph-patched]`: успех и осознанный skip оба не роняют батарею, а вот молчаливое расхождение (ни то, ни другое) — FAIL.
- Fixture-free юнит-тесты (новый `tests/test_kaspi_ip_purpose_rewrite.py`, по образцу `test_kaspi_ip_rounding_policy.py`): `_locate_purpose_amount` на синтетических строках с разными комбинациями разделителей и границ (включая ложные срабатывания вида «190000» внутри номера счёта — уже отфильтровано `_purpose_repeats_amount`'ом, здесь только проверить, что позиция матчится корректно); `_format_purpose_amount` на всех трёх наблюдаемых нотациях; сам gate по ширине — на синтетическом случае, где новая строка заведомо не влезает.
- Реальная валидация: полная battery `verify_kaspi_ip_file.py` на 4 файлах × целях 0.6/1.05/2/5/20, с измерением фактического покрытия (сколько из известных 98 строк переписались vs остались skip) — должно соответствовать оценке ~95/98, задокументированной выше.

## Риски и границы

- **Ложное совпадение старой строки в очереди.** Если два РАЗНЫХ транзакции дают текстуально ИДЕНТИЧНУЮ строку назначения с одинаковым исходным цифровым прогоном (маловероятно, но не исключено) — FIFO-очередь `page_replace_purpose` (тот же паттерн, что у `page_replace_credit`/`page_replace_debit`) разрешает их в порядке появления в документе; та же степень строгости, что уже принята в проекте для сумм.
- **Дебетовые строки.** На измеренном корпусе 0 из 98 случаев — дебетовые; код пишется без предположения «только кредит», чтобы не потребовалось отдельной правки, если найдётся реальный файл с таким случаем.
- **Не расширяется на разрыв строки.** Сознательно, см. «Область охвата» — полный reflow остаётся отдельной, незапланированной задачей.
