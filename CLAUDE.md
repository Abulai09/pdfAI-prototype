## Running the app

**Development server:**

```
pip install -r requirements.txt
python main.py
# Server starts at http://127.0.0.1:8081
```

**Desktop app (pywebview window):**

```
python desktop_app.py
```

**Build Windows .exe:**

```
pyinstaller build.spec
# Output: dist/PDFAI.exe
```

`build.spec`'s `datas` list only bundles `main.py`, `pdf_service.py`, `pdf_service_downscale.py`, and `business_pdf_service.py` — it does **not** list `halyk_pdf_service.py` or `kaspi_ip_pdf_service.py`, even though `main.py` imports both unconditionally. Verify this is still the case (and fix the `datas` list) before shipping a build; a build.spec that's fallen behind an added top-level module would produce an .exe that fails at import time. `desktop_app.spec` also exists (untracked) but has empty `datas`/`hiddenimports` — it is not the spec referenced by any documented build command above; don't assume it's the maintained one without checking with the user first.

**Tests (Halyk, Kaspi ИП, and Kaspi Gold cert-format only, currently — no business-cert test suite yet):**

```
pip install -r requirements-dev.txt
pytest tests/
pytest tests/test_halyk_pdf_service.py -k test_process_then_validate_passes -v  # single test
```

`tests/fixtures/` is not present in every checkout of this repo (it's untracked — there is no `.gitignore` entry for it, it has simply never been committed). Any fixture-dependent test fails with a `FileNotFoundError` until the real PDF fixtures are supplied locally; fixture-independent unit tests (pure-function tests like the day-boundary/CR-byte-slicing ones) still pass on their own. Check `ls tests/fixtures/` before assuming a red `pytest tests/` run means a code regression rather than a missing-fixtures environment.

`tests/test_halyk_pdf_service.py` and `tests/test_kaspi_ip_pdf_service.py` round-trip real PDF fixtures (`tests/fixtures/halyk_nav_*.pdf`, `tests/fixtures/kaspi_ip_*.pdf`) through parse → recalculate → `process_*_pdf` (raw byte rewrite) → `validate_*`, at downscale/upscale/near-no-op targets, plus a few focused unit tests per module (Y-row-grouping boundary and the inline-`Tf`-between-`Td`-and-`Tj` header quirk for Halyk; running-balance-never-negative-on-upscale for Kaspi ИП, since scaleable debit there — unlike Halyk/Kaspi Gold — grows with income). The fixtures are frozen snapshots — if they are ever replaced with newly generated files, rerun `python tests/scripts/print_fixture_targets.py` to recompute floor-safe `target_monthly_income` values for each `ROUNDTRIP_CASES` list, since each generated statement has different random amounts and therefore a different downscale floor (`print_fixture_targets.py` does not yet cover `kaspi_gold_cert_*.pdf` — recompute targets for those manually via `main._verify_pdf(raw)["summary"]["avg_monthly_income"]` if those fixtures are replaced).

`tests/test_pdf_service.py` covers Kaspi Gold (cert-format only — all 5 fixtures have a "Справка об остатке" page 0) via the same round-trip principle, using real fixtures `tests/fixtures/kaspi_gold_cert_original.pdf` (2333 tx/13mo, active card, has `Поступление`/`Зачисление` self-transfer rows), `kaspi_gold_cert_scored.pdf` (same card after one prior `/process` run — floor ends up *below* its now-inflated average, unlike original/small/original2, so scored/scored2 are the only ones exercising a successful downscale), `kaspi_gold_cert_small.pdf` (157 tx/2mo, also has self-transfer rows), and `kaspi_gold_cert_original2.pdf`/`kaspi_gold_cert_scored2.pdf` (3581 tx/13mo, a different real card with *zero* self-transfer rows — added specifically to confirm the self-transfer fixes below don't regress statements that never hit that code path; see `FIXTURES_WITH_SELF_TRANSFER` in the test file for which fixtures exercise which checks). It also pins two Kaspi-Gold-specific fixes found via the original/small fixtures: (1) `parse_full_statement` didn't recognize `Поступление`/`Зачисление` (self-transfer from a Kaspi Deposit sub-account) as transaction types at all — real rows worth up to ~19M ₸ silently vanished from `stmt.transactions`, breaking the balance-identity check even on an untouched original; fixed via `TX_TYPES_SELF_TRANSFER`, classified `is_refund=True` (so it's included in balance math but never scaled as salary, same treatment as a purchase refund). (2) Fixing (1) then exposed a second bug in `process_pdf_bytes_raw`'s raw-byte writer: its own row-type detection (`y_has_refund_type`, matching type-words as `Td`/`Tj` tokens in the *same* content stream as the amount) never finds anything on real Kaspi Gold PDFs — the type/description text isn't among that stream's Tj tokens at all — so a self-transfer's `REFUND_IDENTITY` queue slot (meant to be a same-value no-op so it doesn't steal a salary replacement) never got consumed, permanently blocking the front of that value's FIFO queue and shifting every later same-valued cell onto the wrong transaction. Fixed with `page_refund_cs_ys`, a per-page Y-position filter mirroring the one already used for salary cells (built from `page.get_text("words")`, not the raw content stream, so it works regardless of stream layout). Also found and fixed while adding this suite: `_collect_amount_on_line`'s transaction-parsing call used a hardcoded `x_min=120.0`, calibrated for ≤6-digit amounts — a 7-8 digit amount's leading digit can legitimately render left of x=120, so it was silently dropped (`1 899 000,00` parsed as `899 000,00`); replaced with a dynamic `x_min` computed from that row's own date-token right edge. And: `recalculate_statement` could compute a negative `new_balance_end` after its own running-balance correction step ("Шаг 3") and still let `process_pdf_bytes_raw` write it — but Kaspi Gold's "Доступно на …" header often has no sign glyph in the text at all, and a `-` glyph can't reliably be synthesized (its CID exists only in a non-primary font's CMap, not the one `build_dynamic_cmap`'s `from_unicode` is built from), so the written amount would look positive while `stmt.new_balance_end` was actually negative. Now raises `IncomeTooLowError(reason="post_check_negative_balance")` instead, matching the "solved architecturally, not by patching the cmap" approach `pdf_service_downscale.py`'s own docstring already commits to for its downscale floors.

Both validators' "Целостность стримов" check used to slice a stream's end by searching for the literal text `"endstream"` and guessing a 1-or-2-byte separator via `sd.endswith(b"\r\n"/b"\n")`. Since recompressed zlib output can coincidentally end in `0x0D`, that guess sometimes strips one real payload byte too many, producing a false-positive "N битых стримов" on an otherwise valid, correctly-processed PDF — this was caught by `tests/test_kaspi_ip_pdf_service.py::test_validate_suggested_min_is_achievable`. Both validators now slice by the declared `/Length` instead (the same fix `process_kaspi_ip_pdf`'s own write path already used, per its comment there) — `pdf_service.py`'s Kaspi Gold `_verify_pdf` was not audited for the same pattern and may still have it.

## Quality criteria — the 4 things that matter for ANY generated PDF

Every format (Kaspi Gold, Kaspi ИП, Halyk, business certs) is judged against these four criteria, in order of how catastrophic a failure is. When adding a format, a target range, or a code path, verify against all four — a fix for one has repeatedly turned out to regress or leave a hole in another during this project's audits.

1. **Математика/арифметика (math/arithmetic)** — every balance identity must close: `balance_start + Σ(+) − Σ(−) = balance_end` at the transaction level, the same via the header's own `total_income`/`total_expense` fields, and the running-balance chain must never go negative. This is checked by `main._verify_pdf()` (Kaspi Gold), `kaspi_ip_pdf_service.validate_kaspi_ip()`, `halyk_pdf_service.validate_halyk()` — the same functions `/verify` calls in production. **Running-balance non-negativity must be checked at DAY boundaries, not per-transaction** (see `pdf_service.min_dayend_balance`/`first_negative_dayend`, ported to Halyk as `_halyk_dayend_min_rb`) — none of these statement formats carry intra-day timestamps, so the order of same-date rows in the PDF is arbitrary, and a per-transaction check produces false-positive "overdraft" on a genuinely valid statement (caught for real on an unmodified `gold_statement.pdf`: −54.17 ₸ from 5 debits rendered before 2 same-day covering credits). ISI (income/turnover stability index) is a **soft** signal in Kaspi Gold (reported, doesn't block `passed`) but a **hard** one in Kaspi ИП/Halyk (`validate_kaspi_ip`/`validate_halyk` add it to `issues`) — know which regime you're in before assuming a low ISI on an unmodified original is a bug (it usually isn't — real income/turnover is naturally irregular). Also audit for arithmetic relationships that exist in the data model but aren't covered by any existing check before assuming "all checks pass" means "all math is right" — e.g. the cert-page USD/EUR proportionality to KZT (against the original implied exchange rate) had no check anywhere (production or test) until specifically audited by hand; it turned out correct, but that was verified, not assumed.

2. **Позиционирование цифр и шрифт (text positioning and font)** — no two words on the same visual row may overlap in X after a number grows/shrinks digits (checked programmatically via `find_line_overlaps()` in `tests/scripts/verify_gold_file.py`/`verify_kaspi_ip_file.py`/`verify_halyk_file.py` — same technique, one copy per format), AND font name/size must not change (Halyk's autotest additionally checks this; a bank-issued PDF re-rendering a number in a different font or a shrunk size is a tell). Programmatic geometry checks catch bounding-box overlap but not everything a human notices — **actually render pages to PNG and look at them** (`fitz` `get_pixmap(dpi=150)`, then view the file) at the most extreme target you're testing (largest digit-count growth is where this breaks), not just at the geometry-checker's pass/fail. A short original balance ("1 898,08") growing to 13+ digits after a large upscale was the real bug this class of check was built to catch — it passed the *math* check while visually overflowing the table's left edge.

   **Word-vs-word overlap is not sufficient on its own — three blind spots were found on a real file (`gold_statement.pdf`, 42 pages, cert format) that `find_line_overlaps()` cannot see by construction, and `verify_gold_file.py` now covers all three:** (a) it was only ever called on pages 0 and 1 (`geometry_check(..., extra_pages=[])` — the argument was never filled), so the ~40 pages that actually carry the transaction table were never checked at all; (b) a table border is a *vector line*, not a word, so a number can cross its own cell's frame without colliding with any text — `find_frame_overflows()` now checks words against stroked (`s`/`fs`) cell rects, deliberately ignoring `f` fills since those are invisible and produce false positives; (c) the «Сумма» column is right-aligned, so a *uniform* misalignment shifts every scaled amount together and never overlaps anything — `check_column_alignment()` now asserts the multiset of right edges (x1 of the `₸` glyph per row) is unchanged from the original. That last check is what exposed the real bug below. `check_fonts()` (font name/size multiset vs. original) and `check_natural_rounding()` (criterion 3) were also missing from the Kaspi Gold autotest and are now in it.

   **The X-shift after a number changes width must use the font's REAL digit advance.** `process_pdf_bytes_raw`'s hex writer had `avg_char_width = 4.0` hardcoded for statement pages (only the cert page measured its own width, into `cert_char_width`). ArialMT's digit is `_ARIAL_DIGIT_EM = 0.556` em — 5.28 pt at the body's 9.5 pt and 5.56 pt at the summary table's 10 pt — so 4.0 pt is ~76% of the truth and the left-shift kept undershooting the growth by ~24%, dragging each amount's right edge out of its column proportionally to how much it grew. Compounding it, `original_text` was `.strip()`ed while `new_text` was rebuilt from raw prefix/suffix and kept the cell's trailing spaces («+ 6 500,00 ₸   »), adding a constant phantom left-shift of ~3 spaces. On `gold_statement.pdf` the two errors partly cancelled in the body (right edges landed at 187.5/188.1/189.4 instead of the column's single 190.93 — a visibly ragged column, on every processed file, at every target) and reinforced each other in the header (closing balance crossed its cell's right border by 1.4 pt at ×2, 5.3 pt at ×200). Fixed via `_digit_width_at()`, which reads the actual kegel from the last `/Fx N Tf` before the match (`_ambient_tf`), plus `.strip()` on both sides of the length comparison. After the fix every output reproduces the original's exact edge set (190.93/270.26/300.76) at every target ×0.99…×200, and downscale (which shares this writer via `process_downscale`) is clean too.

   **Summary-table cell capacity above ~1 млрд ₸ — hard-refused, not silently written.** With the alignment correct, a 10-digit amount right-aligned at the column's anchor (x=300.76) starts at x≈205.4, which is 2.3 pt left of that cell's own left border (x=207.7); the cell has 5.5 pt of unused padding on the *right*, so the string fits but the right-aligned position does not. It first appears when the closing balance or total income reaches 10 digits (≈ ×75 of this file's average, i.e. a balance over 1 000 000 000 ₸ — a target that already fails criterion 3 on realism grounds either way). Confirmed on a batch of 13 real cert-format files (`tests/scripts/verify_gold_file.py` run against `testpdf/gold/*`): 9 of 13 hit it at ×50 (one, with an unusually high average income, already at ×10) — always the same two header fields (`total_income`/`balance_end`), always the same 2.31 pt overflow, since the cell's coordinates are a fixed template position shared by every cert-format file, not per-file. Clamping the position was considered and rejected (same reasoning as when this was first found): it would either require mapping the drawn cell rects into content-stream coordinates inside the writer and break the column's right-alignment invariant for that one row (`check_column_alignment` would then fail instead), or shrink the font for just that cell (`check_fonts` would then fail instead) — every fix-in-place trades one geometry class for another. Instead, `recalculate_statement` now raises `HeaderCellOverflowError` (`pdf_service.py`, checked right after the existing `new_balance_end < 0` guard, same architectural spot) whenever either field's magnitude would exceed `_HEADER_CELL_MAX_SAFE_VALUE = 999_999_999`, refusing *before* the PDF is written — the same "solved architecturally, not by patching" precedent as `IncomeTooLowError`. `main.py:/process` catches it and returns HTTP 400 with `reason: "header_cell_overflow"` (does **not** populate `min_desired_income`, since there is no "minimum" here — it's a ceiling, not a floor — so the frontend's floor-specific "Подставить минимум?" auto-fill button correctly does *not* fire for this error; it falls through to the generic error-message display). `verify_gold_file.py`'s battery now treats a caught `HeaderCellOverflowError` as a `cell-guard` row (same non-failing treatment as `floor-guard`/`IncomeTooLowError`), not a FAIL.

3. **Круглые/реалистичные цифры (round / realistic numbers)** — a scaled amount must look like a real transaction a bank would have recorded, not like `amount × K × (1±noise)` rounded to 2 decimals verbatim. This is *not* "always round to whole tenge" — it's "match what THIS format's real, unmodified data actually looks like": Kaspi Gold salary deposits are always whole tenge in human steps (`pdf_service._round_to_natural`: steps of 50/100/500/1000 depending on magnitude); Kaspi ИП scaled amounts round to the nearest 1000 (`_round_amount`), deliberately deferred to a single pass at the very end of `recalculate_kaspi_ip` (rounding mid-loop breaks the balance-correction loop's convergence — small corrections get eaten by the 1000-unit step); Halyk is genuinely mixed — real *nav*-format (Russian-keyword) salaries/seizures are always whole tenge in the same stepped convention as Kaspi Gold, but real *legacy*-format (Kazakh-phrase) salaries genuinely DO carry cents (e.g. `299 374,05 ₸` on a real file) — so `recalculate_halyk()` decides **per-statement, from the statement's own real (unscaled) salary transactions**, not from a hardcoded format label (more robust to variants not yet seen): if none of them have cents, route scaled amounts through `_round_to_natural`; if they do, leave `round(x, 2)` as-is (already realistic there). **The specific bug class to watch for**: a *balance-correction boost loop* (any code that iteratively multiplies an amount by ~1.02–1.05 to fix a negative running balance) is easy to write with a bare `round(x, 2)` since that's what "just fix the number" naturally reads as — but iterating a natural-looking amount through repeated multiplication reliably produces amounts with arbitrary cents. This exact bug was found and fixed in three places this way: `pdf_service.recalculate_statement`'s Шаг 3 (100 of 561 real salary transactions had random cents like `232 682,62 ₸` before the fix), `pdf_service_downscale.recalculate_statement_downscale`'s post-check boost, and would apply to any future correction loop added anywhere in this codebase — check every `round(x * factor, 2)` inside a retry/correction loop against this criterion specifically, they're the highest-risk spot for this class of bug.

4. **(cross-cutting — how the above three must be verified)** — none of them are meaningful if checked only against synthetic/invented data. Every criterion in this project has only ever been validated against **real, unmodified bank statement PDFs** provided by the user (never fixtures invented from scratch) — a real file is what exposes format quirks (self-transfer rows, fee-normalization mismatches, cents conventions, exchange-rate rounding) that a hand-written test case would accidentally "fix" by construction. When a new bank/format/file arrives, re-run all four criteria against it specifically — passing on previously-seen files does not imply passing on a new one; several of the fixes above (day-boundary balance, humped-income floor, natural rounding) were found by testing a real file that a previous test battery had never been run against.

## Architecture

This project is an educational FastAPI application that demonstrates advanced PDF parsing, analysis, and binary editing techniques using fictional bank statement templates created solely for learning and testing purposes.
The application allows a user to load a sample PDF statement, modify transaction values and summary figures, automatically recalculate dependent values, and regenerate a mathematically consistent PDF while preserving its original document structure as closely as possible.

### Module dependency chain

```
main.py
├── pdf_service.py            (Kaspi Gold upscale + shared parse/write utilities)
├── pdf_service_downscale.py  (Kaspi Gold downscale, imports from pdf_service)
├── business_pdf_service.py   (Kaspi business turnover certs, standalone)
├── halyk_pdf_service.py      (Halyk Bank personal statements, standalone)
└── kaspi_ip_pdf_service.py   (Kaspi ИП / sole-proprietor account statements, standalone)
```

`pdf_service_downscale` reuses `pdf_service.process_pdf_bytes_raw` for the actual binary write but provides its own recalculation logic. Never call `process_pdf_bytes_raw` from `pdf_service_downscale` — the dispatch lives in `main.py:/process`.

`halyk_pdf_service` and `kaspi_ip_pdf_service` each reimplement their own parse/recalculate/write pipeline (they do not share `StatementData`/`recalculate_statement` with `pdf_service`), but both reuse `pdf_service.build_dynamic_cmap` and `pdf_service._rebuild_xref_table` for the low-level CMap and xref work.

### Frontend

`static/index.html` is the entire UI — a single-page HTML/JS app. Both `GET /` and `GET /app` serve it (`/app` additionally sets no-cache headers); `static/landing.html` exists but is not currently wired to a route. No build step; edit the HTML directly. The app communicates with the FastAPI backend via `fetch()` calls to `/process`, `/process-business`, `/verify`, `/fix`, etc.

In the desktop (pywebview) build, `window.pywebview.api.save_pdf(name, base64Data)` opens a native Save-As dialog — the JS in `index.html` calls this instead of `<a download>` when `window.pywebview` is detected.

### Processing pipeline (personal statements)

1. **Parse** — `pdf_service.parse_full_statement()` extracts `StatementData`: balances, total income/expenses, and all `Transaction` objects. Uses Y-coordinate grouping of PDF words (±3 px tolerance) plus X-coordinate column detection to identify dates, amounts, and transaction types.

2. **Recalculate** — `recalculate_statement()` (upscale) or `recalculate_statement_downscale()` (downscale). Computes per-month scaling coefficients `K_month = target / month_income` and applies them with ±3% random noise to salary transactions. **Expenses are never scaled** (bank verifies expense categories against Kaspi's own database).

3. **Validate** — `validate_scoring()` checks balance integrity, running balance chain, ISI (income stability index ≥ 0.75), and that balance never goes negative.

4. **Write** — `process_pdf_bytes_raw()` performs the actual modification:
   - Opens raw bytes, finds zlib-compressed content streams
   - Decompresses → regex-replaces hex-encoded text amounts → recompresses
   - Updates `/Length` entries and rebuilds the xref table
   - **Does NOT use `doc.tobytes()`** — that would change line endings, PDF ID, trailer format, breaking binary integrity

`pdf_service.process_pdf_bytes()` (no `_raw`) is a **dead, deprecated** second writer that goes through `doc.update_stream`. It predates cert-format support and was never maintained: measured on a real cert file at ×10 it puts the certificate's KZT amount at x≈4 pt (far outside the table), leaves USD/EUR untouched so `/verify`'s "справка = баланс выписки" cannot close, and lacks the `REFUND_IDENTITY` queue logic so some `+` cells take another row's value. It is no longer imported by `main.py`; don't call it, don't "fix" it — `process_pdf_bytes_raw` is the only correct path.

### Format detection dispatch

`main.py:/process` and `/verify` both open the PDF with `fitz` first and detect the bank/format before doing anything else, in this order:

1. `halyk_pdf_service.detect_halyk_format()` — checks for BIC `HSBKKZKX` / `halykbank.kz` on page 0 → `process_halyk_pdf()` / `validate_halyk()`
2. `kaspi_ip_pdf_service.detect_kaspi_ip_format()` (only if not Halyk) — checks for "Лицевой счет:" + "Входящий остаток" → `process_kaspi_ip_pdf()` / `validate_kaspi_ip()`
3. Otherwise, Kaspi Gold personal statement — falls through to the upscale/downscale dispatch below (`/verify` uses `business_pdf_service.is_business_pdf()` as an additional first check to route to business-cert validation)

### Upscale vs. downscale dispatch (Kaspi Gold)

For the Kaspi Gold personal-statement path, `main.py:/process` pre-parses the PDF and calls `is_downscale_request()`. If target < current average salary income → `pdf_service_downscale.process_downscale()`. Otherwise → `pdf_service.process_pdf_bytes_raw()`.

Downscale has three hard floors: `below_balance_floor`, `too_aggressive` (max 70% reduction), and `post_check_negative_balance`. Violations raise `IncomeTooLowError` which returns HTTP 400.

### CMap / character encoding

Kaspi PDFs use custom font encoding (ArialMT with CID codes, not Unicode). `build_dynamic_cmap()` scans all xref streams for `ToUnicode` entries and builds bidirectional maps `code→char` and `char→code`. The `from_unicode` map is built **only from the primary font (ArialMT, not Bold)** to avoid CID conflicts between F1 and F2 fonts.

### Two Kaspi Gold sub-formats

- **Legacy** — statement starts on page 0
- **Cert** (`detect_statement_format()` returns `"cert"`) — page 0 is a "Справка об остатке" certificate (added to Kaspi Gold PDFs in 2026). Page 0 is parsed separately by `parse_certificate_page()`. The certificate's KZT/USD/EUR balances are updated proportionally using the original exchange rates.

### Business statements (`business_pdf_service.py`)

Completely separate module for Kaspi business account turnover certificates. Parses a monthly Debit/Credit/Balance table, scales only months where Credit < target, adjusts Debit by the same delta to keep `bal_in + Credit − Debit = bal_out` valid.

### Halyk Bank statements (`halyk_pdf_service.py`)

Separate module for Halyk Bank ("Шот бойынша үзінді көшірме", BIC `HSBKKZKX`) personal salary statements. Own dataclasses (`HalykTransaction`, `HalykStatementData`) and own Y-coordinate word-grouping parser (±2 px tolerance vs. ±3 px in `pdf_service`). Uses the same `<XXXX>Tj` hex-string byte-replacement mechanism as Kaspi Gold. Columns: `op_date | proc_date | description | op_amount | KZT | кіріс | шығыс | commission | account`.

`recalculate_halyk()` imports `IncomeTooLowError` from `pdf_service_downscale` and enforces the same three downscale floors as Kaspi Gold (`below_balance_floor`, `too_aggressive` at `_MAX_DOWNSCALE_FACTOR = 0.30`, `post_check_negative_balance` with a running-balance walk sorted by `op_date`) whenever `target_monthly_income` is below the current average salary — gated by the same `if current_monthly_avg > 0 and target_monthly_income < current_monthly_avg` check both places. `validate_halyk()` mirrors the Kaspi Gold `_verify_pdf()` check set: transaction-based balance, header-totals-vs-transactions, an ordered running-balance chain, and a dedicated negative-balance check, in addition to Halyk-specific checks (salary-transactions-found, ISI).

`op_date` has no time component, so — same architectural class as the Kaspi Gold day-boundary fix (see `pdf_service.min_dayend_balance`) — the order of same-date transactions in the PDF is arbitrary. Both `validate_halyk`'s "Баланс ≥ 0" check and `recalculate_halyk`'s `_min_running_balance` correction-loop gate now measure the minimum via `_halyk_dayend_min_rb` (day-boundary, not per-transaction) instead of flagging every individual dip. On the 4 real Halyk files available when this was audited, per-transaction and day-boundary minimums were identical everywhere (no observed divergence) — so this is a defensive hardening for future files, not a fix for an observed false positive here (unlike the Kaspi Gold case, where a real −54.17 ₸ false positive was observed on an unmodified file). Total commission (`stmt.total_commission`) has no date of its own — it's applied as one lump deduction at the very end of the chronology (see the existing front-loading comment) and is folded in as a separate final boundary point, not through the day-boundary helper. Unlike Kaspi Gold's Шаг 3, Halyk's correction loop already raised salary (×1.02) in the deficit direction — it never had the Kaspi-Gold-class "wrong direction" (×0.97 reduction) bug.

**`HalykTransaction` carries TWO currencies, and confusing them corrupts FX rows.** `currency` is the currency of the *sub-account the кіріс/шығыс actually posted to* — it decides whether a row counts toward the tenge balance, and on a continuation line it is deliberately overwritten by the ledger tag `(KZT)`/`(USD)` (see the `_LEDGER_TAG_RE` block in `parse_halyk_statement`). `op_currency` is the currency printed in that row's own «Сумма операции» column and is **never** overwritten. They diverge on «Автоконвертация» rows: op amount in USD, posting in KZT. The hidden-fee normalization (`[FEE-NORM]` in `recalculate_halyk`, which pulls «Расход» down to «Сумма операции» when a template bakes a commission into the debit while the commission column shows `0,00`) was gated on `currency == "KZT"` only, so on a real file (`HALYKformat2`) it rewrote `-4 548,02 ₸` to `-8,85 ₸` and `-1 336,14 ₸` to `-2,60 ₸` — treating the 513.9 ₸/$ exchange rate as a commission. Math still closed (the delta flowed into the closing balance) and every `validate_halyk` check passed, but the output showed 8,85 USD equal to 8,85 ₸ — a visible give-away. The gate now also requires `op_currency == currency`; rows it skips print an `[FX-SKIP]` line with the implied rate (if that rate ever comes out ≈1, the currencies are mislabelled and a real commission is being skipped). A delta-size threshold was rejected as the guard: all 63 genuine fee rows on that file have Δ exactly 200 ₸, which is 40% of the smallest affected transfer (500 ₸), so no percentage cut separates them, and the FX deltas (1 336 ₸) sit too close to any absolute cap. Note the adjacent, deliberately untouched nuance: `is_salary` is decided at parse time from the op-amount currency, *before* any ledger tag is applied, so a credit whose op amount is in USD but which posts in KZT is not treated as scalable salary.

`parse_halyk_statement()` also prints an "⚠️ Неклассифицированные KZT-поступления" diagnostic (mirroring the Kaspi ИП one above), whenever a KZT credit's `is_salary` is `False` — `is_salary` is keyword-based (the Kazakh legacy phrase, or `_NAV_INCOME_KEYWORDS` for nav format) and the list isn't exhaustive; a real unfamiliar income description stays fixed/unscaled (safe for balance math, but the resulting average income may undershoot the requested target).

**When NOTHING matches, that is now a hard refusal, not a silent no-op — and the old no-op path was actively corrupting files.** `recalculate_halyk` used to `return stmt` unchanged when `month_salary` was empty, setting only the four header/balance `new_*` fields. The per-transaction `new_kiri_s`/`new_shyghys` were left at their dataclass default of `0.0`, and `process_halyk_pdf`'s queue builder enqueues a cell whenever `abs(tx.new_shyghys - tx.shyghys) > 0.005` — so **every non-zero amount cell got physically rewritten to «0,00»** while the header totals stayed untouched. Found on a real file (`F4596D1D-…`, a «Спец счет для пособий» account where 100% of income is «Зачисление пособий НАО» and nothing matched `_NAV_INCOME_KEYWORDS`): all 17 expense rows were zeroed, Δ = 863 200 ₸, and every `validate_halyk` check failed. Two layers now prevent it: `recalculate_halyk` initialises `new_kiri_s`/`new_shyghys` to the originals **before any branching** (so no future early return can leak the 0.0 default), and the writer's `_add()` refuses to queue a zero value for a non-`HDR:` key, printing a loud `[⚠️ ПРОПУСК]` instead — writing «0,00» into a real cell is strictly worse than writing nothing. The empty-`month_salary` case now raises `NoScalableIncomeError` (→ HTTP 400 from `main.py:/process`, with the list of unmatched descriptions), because returning the input file unchanged is indistinguishable from success to the caller. `«Зачисление пособий»` was added to `_NAV_INCOME_KEYWORDS` off that same real file — note the list stores whole phrases, not the bare word «Зачисление» (which alone would also swallow «Зачисление с депозита», a self-transfer from the client's own deposit).

**Realistic rounding of scaled amounts is data-driven, not format-hardcoded.** Real *nav*-format Halyk salaries/seizures are always whole tenge (zero cents observed on 3 real files) in steps matching `pdf_service._round_to_natural`'s convention (multiples of 1000 at high magnitudes) — same as Kaspi Gold. Real *legacy*-format (Kazakh phrase) salaries, by contrast, genuinely DO have cents (e.g. `299 374,05 ₸` observed on a real file). Plain `round(x, 2)` after scaling+noise used to produce arbitrary cents on EITHER format (e.g. `43 338 903,25 ₸` on a nav file that never shows cents natively — a give-away that the number was computed, not a real salary deposit). `recalculate_halyk()` now decides per-statement (not per hardcoded format label, which is more robust to variants not yet seen): if none of the statement's own real salary transactions have cents, scaled salary/seizure amounts route through `_round_to_natural` (imported from `pdf_service`) instead of `round(x, 2)`; if the original genuinely has cents, `round(x, 2)` is left as-is (already realistic there). Applies to the initial K-scaling step, the seizure scaling, and the ×1.02 balance-correction boost.

The exact same class of bug — `round(x, 2)` after a balance-correction boost loop leaving random cents on salary amounts that are always whole-tenge in the real data — was also found and fixed in Kaspi Gold's own correction loops: `pdf_service.recalculate_statement`'s Шаг 3 (×1.05 humped-income boost) and `pdf_service_downscale.recalculate_statement_downscale`'s post-check boost (×1.02) now use `_round_to_natural` instead of `round(x, 2)` (found via a real file: 100 of 561 salary transactions had random cents like `232 682,62 ₸` after the Шаг 3 loop ran). Kaspi ИП's own correction loop (`recalculate_kaspi_ip`, the `factor` multiply before `_round_amount`) was checked too and does NOT have this bug — rounding to `_ROUND_UNIT` (1000) is deliberately deferred to a single pass at the very end of the function (see its own comment: rounding mid-loop would make the ±hundreds-₸ corrections get eaten by the 1000-unit step and the correction loop would never converge) — confirmed empirically on a real file: 0 of 1280 scaled transactions were off the 1000-unit grid in the final output.

### Kaspi ИП (sole-proprietor) statements (`kaspi_ip_pdf_service.py`)

Separate module for Kaspi Bank ИП account "Выписка по счету" statements (BIC `CASPKZKA`) — a different table layout from personal Kaspi Gold statements (`№ | Дата | Дебет | Кредит | Получатель/Отправитель | IBAN | БИК | КНП | Назначение`). **Credit vs. debit is NOT keyword-based** — `is_credit` is read from the actual table column via the Y-coordinate threshold (`_credit_debit_threshold()`/`cd_threshold`, since the page is rotated 90° and PyMuPDF returns columns as Y-position, not X), which is far more robust than text matching (there is no `_CREDIT_KEYWORDS` — despite what an earlier version of this doc claimed, no such constant exists in the code). Keyword matching (`_classify_debit_purpose`, against `_DEBIT_SCALE_KEYWORDS`/`_DEBIT_FIXED_KEYWORDS`) applies ONLY to *debit* rows, to decide whether that expense scales proportionally with income (e.g. processing-fee commissions, cash withdrawals) or stays fixed (e.g. the monthly account-maintenance fee, "Погашение комиссии за ведение"). The fallback for a debit purpose matching NEITHER list is `is_scaleable=False` — i.e. treated as fixed/unscaled, the conservative direction (can't push the balance further negative; the risk is the opposite one, see below). Uses the paren-pattern `X Y Td (CID bytes) Tj` replacement mechanism (same as the cert page in `pdf_service`), not the `<XXXX>Tj` hex mechanism.

`parse_kaspi_ip_statement()` prints an "⚠️ Неклассифицированный дебет" diagnostic (count, Σ amount, % of total debit, sample purposes) whenever any debit row's purpose matches neither `_DEBIT_SCALE_KEYWORDS` nor `_DEBIT_FIXED_KEYWORDS` — added after auditing 4 real files found 2.7%–27.5% of debit falling through unclassified (mostly "…Платежи на Kaspi.kz" marketplace/supplier payments — plausibly should scale with turnover, but not confirmed without domain input, so left unscaled rather than guessed). This is observability only, not a behavior change: the fallback (unscaled) was already safe for balance math: an unrecognized debit staying fixed while income grows only makes the statement look *less* proportional (a soft scoring-realism concern, not a correctness bug), never pushes the balance negative. Expanding `_DEBIT_SCALE_KEYWORDS` to cover a newly observed real phrasing is a judgment call about business semantics each time — verify with a real sample before adding, don't guess from the phrase alone.

`recalculate_kaspi_ip()` also enforces the same three `IncomeTooLowError` downscale floors, adapted for the fact that some debit categories (`_DEBIT_SCALE_KEYWORDS`) scale proportionally with credit here (unlike Halyk/Kaspi Gold, where expenses never scale): `below_balance_floor` is computed only against **non-scaleable** debit (`is_credit=False and is_scaleable=False` — fixed commissions plus unclassified debit), since scaleable debit shrinks along with income and can't push the balance further negative. The `too_aggressive` check (only gated for downscale, like the other two banks) and the `post_check_negative_balance` running-balance walk mirror Halyk.

**Important divergence from Halyk/Kaspi Gold:** because scaleable debit (cash withdrawals, self-transfers) grows proportionally with credit here, an *upscale* request can also push the mid-period running balance negative (a debit dated before its matching credit gets bigger too) — something that can't happen in Halyk/Kaspi Gold, where expenses are fixed and upscaling only ever adds money. So the `post_check_negative_balance` running-balance walk and its ×1.02-credit correction/raise in `recalculate_kaspi_ip()` run **unconditionally** (both upscale and downscale), unlike `below_balance_floor`/`too_aggressive` which only apply when target < current average. `validate_kaspi_ip()` has a matching ordered running-balance chain + dedicated negative-balance check (`"Баланс ≥ 0"`), added after a real sample (`Входящий остаток` ≈ 0 ₸) was found to pass the aggregate balance formula while its running balance dipped to −1.2M ₸ mid-period.

**Known unfixed realism gap: the payment purpose repeats the row's own amount.** Real ИП statements routinely restate the invoice sum inside «Назначение платежа» («…по сч №91 от 10.07.26 Сумма 75 000-00 теңге без НДС»). Only the Дебет/Кредит cell is rewritten, so after scaling the row contradicts itself — `Кредит 5 346 000` next to «Сумма 75 000-00». No check catches it: the arithmetic closes and nothing overlaps. `_purpose_repeats_amount()` flags such rows (`KaspiIPTransaction.amount_in_purpose`) and `parse_kaspi_ip_statement` prints the share — **diagnostic only, these rows still scale normally**. The obvious fix (freeze them) was implemented and reverted after measuring it on real files: on `IP4` the pattern covers **42.8% of all credit** (82 rows, 28 275 000 ₸) and on `kaspiIP` 8.8%, and frozen credit cannot be pulled toward the target, so months stop equalizing and ISI drops to 0.50 (IP4) / 0.56–0.59 (kaspiIP) against the hard 0.60 threshold in `validate_kaspi_ip` — every target failed, including ones that passed before. Compensating the per-month target (`K = (target − fixed_month) / scaleable_month`) does not rescue it either: where a month's frozen credit alone already exceeds the target, no K can bring that month down. The only real fix is rewriting the number inside the purpose text as well, which means re-wrapping a narrow multi-line cell — deliberately deferred. Note the detector needs the **full** purpose (it runs before the `purpose[:120]` truncation) and a `_PURPOSE_AMOUNT_MIN = 1000 ₸` floor, since small amounts collide by chance with dates and document numbers inside the text (7 false hits worth 73 ₸ total on IP2/IP3, all matching a date fragment like «за 14/07/2026»).

`process_kaspi_ip_pdf` counts how many copies of a summary value to queue via `_count_standalone()`, not `str.count()`. Plain substring counting matched a short value inside a longer number — on the real `IP3`, «Исходящий остаток 0,15» also occurs as the tail of the transaction amount «60,15», so 2 slots were queued for 1 real cell and the surplus slot printed «1 замен(ы) не применено» on every single run. That message is the only signal for a genuinely unwritten cell, so a permanent false positive silently disarmed it (the output itself was always correct — verified: closing balance rewritten, identity closes). `_count_standalone` rejects neighbouring digits on both sides, including across a thousands-separator space, but deliberately allows a preceding newline (in extracted text the previous cell very often ends in a digit right before ours); undercounting is safe because the caller still floors at `or 1`.

All three personal/sole-proprietor formats (Kaspi Gold, Halyk, Kaspi ИП) now share the same downscale floor contract via `pdf_service_downscale.IncomeTooLowError` — `main.py:/process`'s single `except IncomeTooLowError` handler and the frontend's generic `min_desired_income`-triggered "Подставить минимум?" prompt work unchanged regardless of which module raised it.

### Running-balance non-negativity is checked at DAY boundaries, not per-transaction

Kaspi/Halyk/Kaspi ИП statements have no intra-day timestamps, so the order of transactions sharing one date is arbitrary. Evaluating "balance ≥ 0" after *every* transaction produced false overdrafts: a real unmodified `gold_statement.pdf` dipped to −54.17 ₸ at a single date (five debits rendered before two same-day credits that cover them), which made `/verify` reject a valid statement and tripped the recalc engine's correction loop over 54 tenge. The correct invariant is **balance ≥ 0 at each day boundary** — if a day starts and ends non-negative, some intra-day order (credits before debits) keeps it non-negative throughout. `pdf_service.min_dayend_balance()` (and `first_negative_dayend()`, which also returns the earliest negative day's date) implement this; `main.py:_verify_pdf`'s "Баланс ≥ 0" check and both recalc engines' running-balance walks use them. (ISI is a *soft* check — reported in `_verify_pdf`'s `checks` but NOT added to `issues`, so it does not affect `passed` and never blocks `/process`.) `halyk_pdf_service`/`kaspi_ip_pdf_service` still use their own per-transaction walks (own tx attributes, calibrated against their own fixtures) — same intra-day false-positive class is theoretically possible there but was not reworked without those fixtures to verify against.

### "Humped" income: upscale near the average no longer hits a false floor (Kaspi Gold)

`recalculate_statement` equalizes each month to the flat target (`K_month = target/month_income`), which for a *humped* statement (one month with a very large salary that is spent within that same month) cuts the humped month below what its own fixed expenses need, sending the mid-period running balance negative. The old "Шаг 3" correction then *reduced* salary (×0.97) — the **wrong direction**, which deepened the deficit, drove `new_balance_end` deeply negative, and raised a spurious `post_check_negative_balance` `IncomeTooLowError` (floor) even where a valid result was achievable — so for humped files the floor effectively started around ×2 of average. Now Шаг 3 **raises** salary (like the downscale module's ×1.02) in the deficit month, targeting only salary dated **≤ the deficit day boundary** (later salary can't fund an earlier deficit — raising it would run away to infinity; verified by a synthetic test), preferring the deficit month itself, with a stagnation guard. Balance is now guaranteed ≥ 0 at every day boundary for every achievable target (verified: all 8 real gold fixtures process at ×1.0…×50 with valid balance + geometry). The remaining limit is **ISI (soft)**: for humped files ISI ≥ 0.75 is reachable only from ~×1.1–1.2 of average (mathematically — you cannot both flatten a month and keep its funds for its own spending); below that the PDF is still produced (balance valid) but ISI < 0.75, which `/process` does not block. Only a *structurally* deficient original (tx-level identity doesn't close, e.g. self-transfer sums in the header but not as `Пополнение` transactions) still skips correction and can raise the floor.

### API endpoints

| Endpoint                 | Description                                            |
| ------------------------ | ------------------------------------------------------ |
| `POST /process`          | Personal statement — upscale or downscale              |
| `POST /process-business` | Business turnover certificate                          |
| `POST /verify`           | Validate a scored PDF (math + binary structure)        |
| `POST /fix`              | Surgically fix balance/income mismatch in a scored PDF |
| `GET /journal`           | Operation log (SQLite)                                 |
| `GET /stats`             | Aggregate stats counter                                |

`/fix` (`main.py:_fix_pdf`) is Kaspi-Gold-only — it re-derives `balance_end` from the transaction sum and `total_income` from the balance identity, then rewrites just those two header fields, leaving all transaction rows untouched. Use it when a previously scored PDF's header no longer matches its own transactions (e.g. after manual edits).

### Desktop app

`desktop_app.py` starts the FastAPI server in a background thread, waits for it to bind, then opens a pywebview window. Falls back to the system browser if pywebview fails. DB and static paths are set via env vars pointing to `EXE_DIR` (next to the .exe) and `BUNDLE_DIR` (PyInstaller's `_MEIPASS`). Log is written to `pdfai.log` next to the .exe.

The dev server (`python main.py`) binds to a fixed port 8081. The desktop app (`desktop_app.py`) scans ports 8081–8200 and picks the first free one.

### Key constants

- `INCOME_K = 0.3914` — the bank treats ~39.14% of statement turnover as "income" in scoring. To achieve `desired_income`, the statement must show `desired_income / INCOME_K` as turnover. **Duplicated as a local constant** in `main.py`, `pdf_service_downscale.py`, `halyk_pdf_service.py`, and `kaspi_ip_pdf_service.py` — it is not imported from a shared location, so update all four if it ever changes.
- `SAFETY_MARGIN = 100_000 ₸` — minimum allowed final balance when downscaling.
- `MAX_DOWNSCALE_FACTOR = 0.30` — target cannot be less than 30% of current average.
- `NOISE_PCT = 0.07` (business) — ±7% random variation on generated monthly figures.
